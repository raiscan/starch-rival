# Starch Rival maintenance

Keep this a small compatibility port of canonical poteto pstack. User and consuming repository instructions override workflow defaults. Do not introduce community-fork policies, global activation, extra approval ceremonies, or independent scheduling infrastructure.

- `codex/` and `claude/` are tracked native `starch-rival@starch-rival` plugin packages. Preserve the translations and complete upstream supporting tree. Refresh them and both root marketplace catalogs through `python3 automation/baking/scripts/pstack.py bake`; `build` remains an alias. Never hand-edit generated packages.
- `automation/baking/upstream/` is a canonical `cursor/plugins` Git submodule, with the package at `automation/baking/upstream/pstack/`. Keep its files verbatim. `prepare-sync` advances the gitlink and `automation/baking/upstream.json` together. The manifest, source HEAD, subtree hash, and baked provenance must agree. Use pinned external canonical URLs for GitHub links into the submodule.
- Clone maintenance checkouts with `--recurse-submodules`, or run `git submodule update --init -- automation/baking/upstream`. Initialize each task worktree and repeat after integrating a new pin. Preserve dirty/ignored source work without `--force`. Baking and validation fail clearly on uninitialized or mismatched source rather than fetching implicitly.
- `automation/baking/release.json` is the single authority for the port's semantic version, independently of canonical pstack. Advance it with `bump-version` before release baking, staging, tests, and review. Both native manifests and baked provenance carry that version; marketplace catalogs derive version from the plugin manifests.
- `automation/baking/port/` owns platform, setup, and model defaults; `scripts/` and `tests/` own packaging, legacy installation, sync, and delivery contracts. Native Claude registers skills and sets `agents: []`; the preserved Cursor agent prompts remain reference material. Keep upstream invocation policy and support bytes except for defined adaptations.
- Keep exact `claude-sonnet-5-5` as the required independent reviewer. Read `automation/baking/port/PORT.md` for routes and unavailable-model handling. Obtain its read-only review of the final substantive code/workflow changes before delivery. One review of unchanged final work is enough; material changes or unresolved findings justify another review. The tooling does not attest that review occurred.
- Use isolated `.worktrees/` branches named `feature/ai-*` or `bugfix/ai-*`. Never switch the main workspace branch or overwrite unrelated work. Fetch and fast-forward the primary checkout's current branch before work. Account for every change before cleanup.
- Run `python3 -m unittest discover -s automation/baking/tests -v`, bake, and validate. Stage the complete intended changes, including specific ignored support files when necessary, then run `python3 automation/baking/scripts/pstack.py validate --tracked`. It checks indexed publication inventory, bytes, and modes as well as the defined adaptations. Add focused checks for changed routing, references, invocation, installation, and sync behavior. Attribute disputed failures by identity and failure against the baseline; new or worsened failures block integration. Do not repeat unchanged checks merely as ceremony.
- Maintenance resolves the primary checkout through Git's worktree inventory and shares its lock, fetch cache, and candidate worktrees. The existing Hermes job keeps its saved working directory, Sol model, reviewer route, schedule, helper configuration, and history. `delivery.py precheck` refreshes clean primary `main` from `origin/main`, refreshes an already-configured native Codex plugin on that same host when available, then emits the canonical subtree check JSON. Missing installations are skipped; failures stay visible.
- The owner has authorized the Hermes job to adapt/version/bake/test a candidate, obtain exact Sonnet review of its final staged Git tree, commit those reviewed contents, fast-forward primary `main`, verify the integrated result, and push only `main` through `delivery.py publish`. No PRs, candidate plugin installations, other branch pushes, or user model/credential/trust/schedule changes are included. A stale review, moved base, dirty source, or new/worsened test failure blocks delivery. Follow `automation/baking/sync-task.md` for the exact command contract and reporting.
- Source preparation moves only the candidate's submodule and cannot mutate active legacy snapshots. Compare pstack's subtree, not unrelated monorepo changes. `candidate_pending` suppresses repeated agents/tests/review for an already-prepared tree; it does not mean review or delivery succeeded. Preserve interrupted work for explicit resumption; newer trees receive separate candidates. Publication's `cleanup_pending` is unfinished cleanup, not permission to delete unknown work. After verified push, inspect and account for task-owned work before removing its merged worktree/branch and pruning metadata.
- Prefer native marketplace installation and delivery. Claude uses opted-in marketplace auto-update; the maintainer's workstation uses the existing user-systemd scheduler for hourly native Codex marketplace refresh without inference. Hermes runs on a different host. `automation/updates/` describes client delivery; repository changes do not rewrite live jobs or settings.
- The legacy installer remains an explicit fallback from clean primary `main`. It validates and copies baked packages without rebaking, creates immutable `.cache/installed/` snapshots, and owns only its exact skill links. Retire those links only after native plugins are verified, using `retire-links`; preserve snapshots and foreign skills. Do not claim an install, scheduler activation, review, push, or completed cleanup that did not occur.
